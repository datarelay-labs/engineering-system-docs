# Tool stack

The system is built around a small number of tools with deliberately different roles.

~~~mermaid
flowchart LR
    O["Owner"] <--> C["ChatGPT<br/>Think · Design · Review"]
    C --> U["Cursor<br/>Implement"]
    U --> G["GitHub / Tests / CI<br/>Durable Evidence"]
    G --> C
    C -. verify local reality .-> D["Desktop Commander<br/>Dev Server Audit"]
    U -. completion signal .-> T["Telegram"]
~~~

The split is intentional: exploratory thinking stays lightweight, implementation starts after scope is bounded, and evidence is stored outside either AI conversation.

## ChatGPT

Primary planning and review environment.

Use it for requirements, architecture, design, documentation, test planning, code review, release reasoning, and deciding what Cursor should do next.

The normal mode is conversational Chat. Long-running Work mode is reserved for cases where it is explicitly useful rather than being the default for every engineering discussion.

## Cursor

Primary implementation agent.

Cursor receives repository context, edits code, runs affected tests, and updates the active Work Packet.

The normal handoff does not require the owner to type a Cursor command. When the owner says "Cursor에 넘겨줘", ChatGPT updates the repository-scoped Work Packet, prepares the correct worktree, starts Cursor CLI on the authorized development server, and hands it the `/work-resume` workflow.

Cursor is used in two forms:

- **Cursor desktop on macOS** for long desk sessions.
- **Cursor CLI on the development Linux server** for mobile or remote sessions, using a Cursor-native persistent session for ChatGPT-orchestrated handoffs.

### Cursor persistent sessions

Normal ChatGPT-orchestrated launch:

~~~bash
cd <target-worktree>
agent persist /work-resume
agent persist list
agent persist attach <session>
~~~

ChatGPT verifies the target worktree first and must confirm the session appears in `agent persist list` before reporting a successful handoff. `agent persist stop <session>` intentionally terminates the running session.

A non-persistent `--print` process is not the normal handoff because the owner cannot later attach to that session; ChatGPT must not use that fallback unless the owner explicitly permits it.

## Telegram

Cursor is configured to send a Telegram message when a task completes.

Telegram is used only as a **completion signal** so the user can leave long-running implementation or test work unattended and return when action is required.

It is not used as engineering state, evidence, or a source of truth.

## GitHub

The durable engineering backbone.

GitHub stores:

- code and Git history
- product specifications and ADRs
- tests and regression coverage
- pull requests and review
- CI evidence
- exact-HEAD release evidence
- repository-scoped AI Work Packets

This is where the workflow eventually returned after experiments with more document-centric project management.

## Desktop Commander Remote MCP

[Desktop Commander Remote MCP](https://mcp.desktopcommander.app) gives ChatGPT access to an authorized remote machine through controlled filesystem and terminal operations.

In this workflow it is used mainly for development-server audit:

~~~text
ChatGPT
  -> Desktop Commander
  -> development Linux host
  -> inspect repo / files / processes / tests
  -> compare runtime state with GitHub and Cursor claims
~~~

This is valuable when a GitHub-only review cannot prove what is actually present or running on the development host.

Access should be constrained to authorized directories and commands. Read-first inspection is preferred for audit work.

## Athena

Athena is the planned searchable knowledge layer for decisions, rationale, and cross-project history.

It is intentionally **derived knowledge**, not the canonical source of truth.

GitHub still wins for current code, specifications, tests, and release evidence.

## Why not one tool for everything?

Earlier workflows tried to let one coding agent handle brainstorming, implementation, debugging, and all context at once.

That was convenient, but open-ended conversations could consume a large amount of tokens before the implementation target was stable. When the prompt was not tightly bounded, cost could rise while output quality still varied.

The current split keeps high-level thinking lightweight and uses the implementation agent only after the work is well defined.
