# 빠른 시작

처음부터 모든 선택 도구를 설치할 필요는 없습니다.

먼저 durable state가 생기는 가장 작은 loop부터 구성합니다.

~~~mermaid
flowchart LR
    A["ChatGPT<br/>설계"] --> B["GitHub AI Work Packet"]
    B --> C["ChatGPT<br/>구현·테스트"]
    C --> D["Affected Tests"]
    D --> E["GitHub<br/>Commit / PR / CI"]
    E --> A
~~~

## 0. GitHub 접근부터 준비

Session Continuity는 ChatGPT가 repository-scoped GitHub Issue를 읽고 갱신할 수 있어야 합니다.

- ChatGPT는 Work Packet을 만들고 갱신할 수 있도록 대상 GitHub 저장소에 접근할 수 있어야 합니다.
- 기본 구현 경로에는 Cursor가 필요하지 않습니다.
- 선택적 Cursor 호환 경로를 명시적으로 활성화하는 경우에만 `/work-resume`용 GitHub integration 또는 인증된 `gh`가 추가로 필요합니다.
- GitHub 접근이 없다면 과거 Handoff를 다시 복붙해서 복원하지 말고 GitHub 접근부터 구성합니다.

## 1. AI에게 저장소 적용 요청

의도한 시작 방법은 버전과 무관하게 동일하게 단순합니다.

~~~text
이 프로젝트에
https://github.com/datarelay-labs/engineering-system
을 적용해줘.
~~~

AI는 template을 무작정 복사하는 것이 아니라 canonical adoption 절차를 따라야 합니다.

~~~text
Repository Inventory
  -> 기존 AI / Engineering Rule 분류
  -> Native Test / CI / Release Flow 탐색
  -> Project-specific / stricter invariant 보존
  -> Shared CI 또는 Native CI 명시적 선택
  -> 부족한 Engineering System surface bootstrap
  -> Adoption Qualification
~~~

Deterministic helper로 먼저 read-only audit을 할 수 있습니다.

~~~bash
python tools/adopt.py --root /path/to/project --audit
~~~

Managed adoption은 제공된 URL에서 Engineering System을 가져온 뒤 버전과 변경되지 않는 기준 SHA를 함께 고정합니다. 또한 shared/native CI 중 무엇이 검증을 담당하는지, merge gate 상태와 운영 요구사항을 명시해 AI가 파일 존재 여부만 보고 책임 범위를 추측하지 않게 합니다. 새 저장소는 먼저 Git 저장소를 만들고, `--allow-no-tests`는 실행 가능한 테스트가 아직 없을 때만 임시로 사용합니다.

## 2. Managed Adoption이 준비하는 것

Managed adoption은 다음 surface를 준비합니다.

~~~text
AGENTS.md
.engineering/project.yaml
.engineering/tests.yaml
.engineering/release.yaml
.cursor/rules/engineering-system.mdc
.cursor/commands/resume.md
.github/ISSUE_TEMPLATE/ai-work-packet.md
.github/workflows/engineering-system.yml
~~~

Project-native release qualification command가 명확하면 release preflight/gate wiring도 추가할 수 있습니다.

기존 프로젝트 파일은 기본적으로 덮어쓰지 않습니다. 변경 중인 worktree, 검토하지 않은 AI 규칙, 모호한 테스트 명령, 기존 CI의 shared/native 담당 범위 미확정, 파괴적인 업그레이드처럼 안전하게 판단하기 어려운 상황에서는 작업을 중단합니다.

## 3. Session Continuity

기본 continuity surface는 repository-scoped AI Work Packet입니다.

~~~text
.github/ISSUE_TEMPLATE/ai-work-packet.md
~~~

선택적 Cursor 호환 경로를 명시적으로 사용할 때만 `.cursor/commands/resume.md`와 관련 Cursor 규칙을 사용합니다.

## 4. ChatGPT Custom Instructions는 짧게

Custom Instructions에 Engineering System 전체 내용을 복사해 넣지 않습니다.

Global instruction은 routing만 담당하면 됩니다.

- target repository 먼저 식별
- canonical Engineering System 사용
- 현재 작업에 필요한 context만 로드
- handoff/resume은 repository Work Packet을 사용하고 구현 handoff 직전에 사용자의 최신 명시적 요청으로 `TASK_KIND` / `OWNER_INTENT`를 동기화
- 실행 전에 실제 Git/GitHub 상태 재검증
- 실행하지 않았거나 다른 HEAD의 evidence를 PASS로 사용하지 않기

## 5. 첫 작업 실행

~~~text
ChatGPT:
"Engineering System 계속"
  → active Work Packet + repository/branch/HEAD 재확인
  → ChatGPT가 직접 구현·테스트·감사

ChatGPT:
"계속"
  → exact HEAD, PR/CI/review를 다시 확인하고 Next Action 계속
~~~

긴 handoff prompt를 복사하지 않고 같은 Work Packet을 기준으로 이어지면 continuity path가 정상입니다. 선택적 Cursor 호환 경로가 필요한 경우에만 [모바일 & 원격 작업](/ko/mobile-remote-workflow)의 별도 opt-in 절차를 사용합니다.

## 구현 전에 확인할 것

Owner와 AI는 최소한 다음을 알아야 합니다.

~~~text
Change Type
Affected Domain
Public Contract
Persisted State
Security Boundary
Operational Impact
Required Tests
~~~

그 다음 가장 작은 올바른 변경을 하고, 오류를 가장 빨리 증명할 수 있는 deterministic check부터 실행합니다.

<Note>
  Product scope, 최종 의사결정, release 승인, human UX 판단은 Owner에게 남습니다. AI는 engineering process를 지원하며 scope를 임의로 넓히지 않습니다.
</Note>
