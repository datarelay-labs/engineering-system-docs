# 일상 작업 흐름

기본 흐름은 단순합니다.

~~~mermaid
flowchart LR
    A["ChatGPT<br/>브레인스토밍·설계"] --> B["AI Work Packet<br/>Next Action"]
    B --> C["ChatGPT<br/>구현·테스트"]
    C --> D["Affected Test<br/>빠른 검증"]
    D --> E["GitHub<br/>Commit·PR·CI"]
    E --> F["ChatGPT<br/>결과 리뷰"]
    F --> A
    F -. 필요 시 .-> G["Desktop Commander<br/>개발 서버 직접 감사"]
~~~

<Steps>
  <Step title="ChatGPT에서 먼저 생각한다">
    문제, 요구사항, 아키텍처, UX, 문서, 테스트 전략과 범위를 구현 전에 충분히 정리합니다.
  </Step>

  <Step title="AI Work Packet을 만든다">
    구현이 필요한 시점에는 긴 handoff 프롬프트 대신 해당 저장소의 [AI Work] Issue를 갱신합니다. 구현 시작 직전에 사용자의 가장 최근 요청을 기준으로 `TASK_KIND`, `OWNER_INTENT`, `INTENT_REVISION`, `CHANGE_RISK`, `IMPLEMENTER`를 맞추고, `Next Action`이 실제로 그 요청을 전진시키는지 확인합니다. 이전에 남아 있던 릴리스·정리·테스트 단계가 자동으로 다음 작업이 되어서는 안 됩니다.
  </Step>

  <Step title="ChatGPT가 기본 구현을 수행한다">
    기본 Work Packet은 `IMPLEMENTER=CHATGPT_CHAT`입니다. ChatGPT가 정확한 저장소·worktree·branch·HEAD 권한 경계를 확인한 뒤 직접 구현하고 affected test를 실행합니다. `Cursor에 넘겨줘`는 현재 packet에서만 `IMPLEMENTER=CURSOR`로 전환하는 명시적 opt-in입니다.
  </Step>

  <Step title="가장 싼 검증부터 한다">
    affected deterministic test부터 실행하고, release boundary가 아니면 불필요한 Full Suite를 피합니다.
  </Step>

  <Step title="ChatGPT로 돌아온다">
    일반적인 이어가기는 사용자가 `계속`이라고 말하면 됩니다. `Cursor 끝났어. 계속`은 명시적으로 Cursor를 활성화한 작업 뒤에만 사용하며, ChatGPT가 Work Packet과 실제 GitHub/HEAD 상태를 다시 검증합니다.
  </Step>
</Steps>

## 사용자가 기억할 명령

~~~text
ChatGPT:
"계속"
  → active Work Packet과 실제 branch/HEAD/PR/CI를 확인
  → ChatGPT가 직접 구현·테스트·감사 계속

상태 확인:
"진행사항 확인해줘"
"Full Suite 언제 끝날 것 같아?"
  → ChatGPT가 승인된 개발 서버와 GitHub 상태를 직접 확인
  → 현재 작업, 진행률, blocker, 근거 기반 완료 예상 시간 범위를 요약

새 ChatGPT:
"DRLink 계속"
~~~

Cursor 호환 경로는 현재 Work Packet에서 owner가 명시적으로 opt-in한 경우에만 `Cursor에 넘겨줘`와 `/work-resume`을 사용합니다.

자세한 모바일·원격 관찰 방법은 [모바일 & 원격 작업](/ko/mobile-remote-workflow)을 참고합니다.

진행 상황을 보기 위해 사용자가 개발 서버에 직접 접속할 필요는 없습니다. 상태만 확인하면 ChatGPT가 현재 프로세스/테스트, 정확한 HEAD, worktree, Work Packet, PR/CI를 확인해 요약할 수 있습니다. 완료 예상 시간은 현재 테스트 위치나 남은 장시간 테스트처럼 확인 가능한 근거가 있을 때만 범위로 제시합니다.

## 왜 ChatGPT를 먼저 쓰는가

아이디어가 아직 흔들리는 단계에서 coding agent를 오래 돌리면 구현 전에 context와 비용이 커질 수 있습니다.

그래서 요구사항·설계·문서·테스트 전략과 repository 수정까지 ChatGPT에서 이어가는 것이 기본입니다. Cursor가 유리한 특정 작업에만 owner opt-in과 `IMPLEMENTER=CURSOR`를 함께 요구합니다.

## 검증 흐름

~~~mermaid
flowchart TD
    C["일반 변경"] --> A["Affected Tests"]
    A --> P["Cheap PR Guardrails"]
    P --> M["Merge"]

    R["Release Candidate"] --> F["Fast Preflight"]
    F --> Q["Full Deterministic Qualification"]
    Q --> L["Lifecycle / Platform"]
    L --> E["Performance / Resilience"]
    E --> O["Operational E2E"]
    O --> H["Exact-HEAD Release"]
~~~

Known deterministic blocker가 있으면 expensive downstream qualification을 시작하지 않습니다.

## Review feedback도 Merge Gate다

Engineering System 1.5.1부터 review 처리는 상태값이 아니라 **실제 review 내용**을 기준으로 합니다.

병합 또는 최종 완료 전에 현재 구현 agent는 PR 리뷰, 일반 댓글, 인라인 피드백을 확인합니다. 사람 리뷰어나 설정된 자동 리뷰어의 수정이 필요한 지적은 다음 둘 중 하나로 처리해야 합니다.

- 실제 수정 후 affected validation을 다시 실행
- non-actionable / out of scope / incorrect라고 판단한다면 짧은 근거를 남겨 disposition

`COMMENTED`나 advisory 상태 자체가 자동 PASS 또는 FAIL을 의미하지 않습니다. **내용이 기준**이며, actionable review feedback이 미처리된 상태에서는 merge하거나 workstream을 완료 처리하지 않습니다.
