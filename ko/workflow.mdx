# 일상 작업 흐름

기본 흐름은 단순합니다.

~~~mermaid
flowchart LR
    A["ChatGPT<br/>브레인스토밍·설계"] --> B["AI Work Packet<br/>Next Action"]
    B --> C["Cursor<br/>구현"]
    C --> D["Affected Test<br/>빠른 검증"]
    D --> E["GitHub<br/>Commit·PR·CI"]
    E --> F["ChatGPT<br/>결과 리뷰"]
    F --> A
    F -. 필요 시 .-> G["Desktop Commander<br/>개발 서버 직접 감사"]
~~~

<Steps>
  <Step title="ChatGPT에서 먼저 생각한다">
    문제, 요구사항, 아키텍처, UX, 문서, 테스트 전략과 범위를 구현 전에 충분히 정리합니다.
  </Step>

  <Step title="AI Work Packet을 만든다">
    구현이 필요한 시점에 긴 Cursor prompt 대신 repository-scoped [AI Work] Issue를 갱신합니다. Cursor handoff 직전에 사용자의 가장 최근 명시적 요청을 기준으로 `TASK_KIND`와 `OWNER_INTENT`를 새로 맞추고, `Next Action`이 실제로 이를 전진시키는지 확인합니다. 예전에 남아 있던 release/cleanup/test 단계가 자동으로 다음 작업이 되면 안 됩니다.
  </Step>

  <Step title="ChatGPT가 Cursor를 시작한다">
    「Cursor에 넘겨줘」라고 하면 ChatGPT가 Work Packet·worktree를 준비한 뒤 개발 서버에서 Cursor CLI를 시작하고 `/work-resume`을 넘깁니다. 소유자가 평소에 `/resume`이나 `/work-resume`을 직접 칠 필요는 없습니다.
  </Step>

  <Step title="가장 싼 검증부터 한다">
    affected deterministic test부터 실행하고, release boundary가 아니면 불필요한 Full Suite를 피합니다.
  </Step>

  <Step title="ChatGPT로 돌아온다">
    사용자는 "Cursor 끝났어. 계속"이라고 말하면 됩니다. ChatGPT는 Work Packet과 실제 GitHub 상태를 다시 확인합니다.
  </Step>
</Steps>

## 사용자가 기억할 명령

~~~text
ChatGPT:
"Cursor에 넘겨줘"
  → ChatGPT가 Work Packet을 준비하고 Cursor CLI(/work-resume)를 시작

실행 중 Cursor를 직접 보기:
ssh <development-server>
agent persist list
agent persist attach <session>

또는 ChatGPT에게 직접 확인 요청:
"Cursor 진행사항 확인해줘"
"Full Suite 언제 끝날 것 같아?"
  → ChatGPT가 승인된 개발 서버의 Cursor/session/test 상태와 GitHub 상태를 직접 확인
  → 현재 작업, 진행률, blocker, 근거 기반 완료 예상 시간 범위를 요약

ChatGPT:
"Cursor 끝났어. 계속"
  → ChatGPT가 GitHub/CI/PR/issue/worktree를 독립 재검증

새 ChatGPT:
"DRLink 계속"
~~~

자세한 모바일·원격 관찰 방법은 [모바일 & 원격 작업](/ko/mobile-remote-workflow)을 참고합니다.

사용자는 진행 상황을 보기 위해 반드시 `agent persist attach`를 직접 실행할 필요는 없습니다. 상태 확인만 필요하면 ChatGPT가 실제 Cursor process/session, 현재 test, exact HEAD, working tree, Work Packet, PR/CI를 확인한 뒤 요약할 수 있습니다. 완료 시간 질문에는 현재 test 위치와 남은 long-running test 같은 관측 가능한 근거로 **범위형 ETA**를 제공하며, 근거가 부족하면 임의의 시간을 만들지 않습니다.

## 왜 ChatGPT를 먼저 쓰는가

아이디어가 아직 흔들리는 단계에서 coding agent를 오래 돌리면 구현 전에 context와 비용이 커질 수 있습니다.

그래서 요구사항·설계·문서·테스트 전략은 가벼운 대화로 먼저 수렴시키고, 실제 repository 수정이 필요한 시점에만 Cursor에게 bounded task를 넘깁니다.

## 검증 흐름

~~~mermaid
flowchart TD
    C["일반 변경"] --> A["Affected Tests"]
    A --> P["Cheap PR Guardrails"]
    P --> M["Merge"]

    R["Release Candidate"] --> F["Fast Preflight"]
    F --> Q["Full Deterministic Qualification"]
    Q --> L["Lifecycle / Platform"]
    L --> E["Performance / Resilience"]
    E --> O["Operational E2E"]
    O --> H["Exact-HEAD Release"]
~~~

Known deterministic blocker가 있으면 expensive downstream qualification을 시작하지 않습니다.

## Review feedback도 Merge Gate다

Engineering System 1.5.1부터 review 처리는 상태값이 아니라 **실제 review 내용**을 기준으로 합니다.

Merge 또는 terminal completion 전에 현재 구현 agent가 machine-observable PR review submission, top-level comment, inline feedback을 확인합니다. 사람 reviewer나 설정된 automated reviewer의 actionable finding은 다음 둘 중 하나로 처리해야 합니다.

- 실제 수정 후 affected validation을 다시 실행
- non-actionable / out of scope / incorrect라고 판단한다면 짧은 근거를 남겨 disposition

`COMMENTED`나 advisory 상태 자체가 자동 PASS 또는 FAIL을 의미하지 않습니다. **내용이 기준**이며, actionable review feedback이 미처리된 상태에서는 merge하거나 workstream을 완료 처리하지 않습니다.
