# Session Continuity

대화 history는 임시 작업 공간으로 취급합니다.

현재 workstream의 durable state는 같은 repository의 GitHub Issue인 **AI Work Packet**에 둡니다.

## Before → After

~~~mermaid
flowchart LR
    subgraph BEFORE["이전"]
      A1["ChatGPT 긴 대화"] --> A2["긴 Cursor Prompt"]
      A2 --> A3["Cursor 결과 복사"]
      A3 --> A4["긴 Handoff Prompt"]
      A4 --> A5["새 ChatGPT"]
    end

    subgraph AFTER["현재"]
      B1["ChatGPT"] --> B2["GitHub AI Work Packet"]
      B2 --> B3["Cursor /work-resume"]
      B3 --> B2
      B2 --> B4["ChatGPT 계속"]
    end
~~~

이전 방식은 토큰을 쓰고 사용자가 계속 복사·붙여넣기를 해야 했습니다.

현재 방식은 같은 Work Packet을 ChatGPT와 Cursor가 함께 사용합니다. 「Cursor에 넘겨줘」라고 하면 ChatGPT가 Work Packet을 준비한 뒤 Cursor CLI를 시작하고 `/work-resume`을 넘깁니다. 소유자가 평소에 명령을 직접 칠 필요는 없습니다.

## Work Packet 단위

한 repository에 하나가 아니라 **workstream 하나당 하나**입니다.

~~~text
[AI Work] v2.4.0 Release Closure
[AI Work] Website Refresh
[AI Work] Connector Expansion
~~~

Work Packet은 일기가 아니라 current-state record입니다.

## 기본 구조

```text
PACKET_VERSION=2
TARGET_REPO=owner/repository
WORKSTREAM=stable-slug
STATUS=ACTIVE|PAUSED|BLOCKED|COMPLETE
BRANCH=branch-name|N/A
TASK_KIND=DESIGN|DEVELOPMENT|TEST|REVIEW|RELEASE|OPERATIONS|ADOPTION|DOCUMENTATION|CLEANUP|MIXED
OWNER_INTENT=사용자가 지금 명시적으로 요청한 작업 한 줄
LAST_VERIFIED_HEAD=sha

Goal
Current State
Next Action
Constraints
Canonical References
Latest Evidence
Blockers
```

## Work Packet Lifecycle

~~~text
ACTIVE   -> Open Issue
PAUSED   -> Open Issue
BLOCKED  -> Open Issue
COMPLETE -> Close Issue
~~~

새로운 독립 workstream일 때만 새 Issue를 만듭니다. 대화창이 새로 열렸다는 이유로 Work Packet을 새로 만들지 않습니다.

여러 프로젝트의 handoff를 한 중앙 repository에 섞어두지 않습니다. 각 product repository가 자신의 Work Packet namespace입니다.

## Fail-closed Resume

~~~mermaid
flowchart TD
    A["현재 Repository 확인"] --> B["현재 Branch 확인"]
    B --> C["Open [AI Work] Issue 검색"]
    C --> D{"정확히 1개 ACTIVE match?"}
    D -- "Yes" --> E["실제 HEAD / Dirty / PR / CI 재검증"]
    E --> F["Next Action 수행"]
    D -- "0개 또는 2개 이상" --> G["STOP / 최소 확인 요청"]
~~~

LAST_VERIFIED_HEAD는 참고값일 뿐 현재 truth로 사용하지 않습니다.

Work Packet v2는 오래된 handoff scope가 그대로 실행되는 것도 막습니다. Cursor handoff 전에 ChatGPT가 사용자의 **가장 최근 명시적 요청**을 기준으로 `TASK_KIND`와 `OWNER_INTENT`를 갱신하고, `Next Action`이 stable `Goal`과 현재 intent를 실제로 전진시키는지 확인합니다. 서로 충돌하면 구현 agent는 예전 release/cleanup/validation 단계로 진행하지 않고 `WORK_PACKET_SCOPE_MISMATCH`로 중단합니다.

`STATUS`는 `ACTIVE`, `PAUSED`, `BLOCKED`, `COMPLETE` 네 개만 사용합니다. `CURSOR_READY`, `WAITING`, `DONE` 같은 값을 새 lifecycle 상태로 만들지 않습니다. Cursor 준비 상태는 `STATUS=ACTIVE` + 유효한 `Next Action`으로 표현하고, machine-observable wait는 Current State/Latest Evidence에 기록합니다.

Repository 구현을 시작하려면 local shell/process와 Git context가 실제로 동작해야 합니다. shell을 시작할 수 없으면 Athena나 unrelated repository, 과거 transcript를 뒤지는 대신 `ENVIRONMENT_BLOCKER`로 중단합니다.

## 왜 HANDOFF.md가 아닌가

release candidate가 exact-HEAD qualification을 요구할 때 committed HANDOFF 파일을 수정하면 product HEAD 자체가 바뀝니다.

GitHub Issue를 갱신하면 source HEAD를 바꾸지 않고도 current coordination state를 유지할 수 있습니다.

## ChatGPT 대화 Handoff

대화창이 길어져도 별도 Handoff Issue나 giant continuation prompt를 만들지 않습니다.

현재 Work Packet만 최신화하고 새 대화에서 다음처럼 시작하면 됩니다.

~~~text
DRLink 계속
~~~

새 ChatGPT는 active Work Packet과 실제 GitHub 상태를 다시 확인한 뒤 Next Action부터 이어갑니다.
