# 개선 과정과 Lessons

이 시스템은 처음부터 큰 프로세스 framework를 설계한 것이 아니라 반복되는 불편을 하나씩 제거하면서 만들어졌습니다.

## Before → After

| 문제 | 이전 방식 | 현재 방식 |
|---|---|---|
| AI가 계획 문서를 잘 안 읽음 | Charter, WBS, Roadmap | 작은 mandatory repository entrypoint |
| 범위 / 로드맵 불일치 | 계획 문서 수동 유지 | Git / Spec / Test 중심 |
| 구현 이유가 사라짐 | Chat에만 결정이 남음 | Spec / ADR + Athena |
| Cursor 프롬프트가 너무 김 | 매번 복붙 | GitHub AI Work Packet |
| ChatGPT 작업 전달이 너무 김 | 긴 이어가기 프롬프트 | 같은 Work Packet + 짧은 시작 문구 |
| 아이디어 단계부터 coding agent 비용 증가 | 한 도구에서 전부 수행 | ChatGPT 설계 → Cursor 구현 |
| 서버 실제 상태 확인이 어려움 | shell output 복붙 | Desktop Commander 직접 감사 |
| 이동 중 긴 작업 유지 어려움 | terminal/device 종속 | Cursor CLI + `agent persist` + 휴대폰 SSH |
| Cursor 완료 여부 반복 확인 | terminal polling | Telegram 완료 알림 |
| Full Suite 과다 실행 | 변경마다 broad validation | affected-first, release boundary full qualification |
| 오래된 PASS 재사용 위험 | 과거 검증 결과 | 현재 HEAD 기준 검증 |

## 변화 흐름

~~~mermaid
flowchart LR
    A["많은 계획 문서"] --> B["GitHub Source of Truth"]
    B --> C["Athena<br/>결정·히스토리 검색"]
    C --> D["AI Work Packet<br/>세션 연속성"]
    D --> E["Cursor /resume"]
    E --> F["Desktop Commander<br/>독립 감사"]
    F --> G["agent persist + Telegram<br/>모바일 운영"]
~~~

## 왜 GitHub 중심으로 돌아왔는가

Project Charter, WBS, Roadmap은 생각을 정리하는 데는 도움이 되었지만 실제 agent가 항상 읽지 않았습니다.

반면 GitHub에는 이미 버전 관리된 소스, PR, 테스트, 변경되지 않는 commit, CI, Issue와 릴리스 이력이 있었습니다.

그래서 별도의 두 번째 source of truth를 만들기보다 GitHub를 중심에 두는 쪽으로 돌아왔습니다.

## Tela → Athena

결정 이유와 cross-project history를 검색할 knowledge layer는 여전히 필요했습니다.

Tela를 검토했지만 source 개수 제약 때문에 intended scale과 맞지 않아 Athena로 이동하는 방향을 선택했습니다.

Athena는 검색 계층이며 GitHub의 authority를 대체하지 않습니다.

## 다음 병목은 작업 맥락 전달이었습니다

GitHub 중심 구조가 잡힌 뒤 가장 큰 반복 비용은 다음이었습니다.

~~~text
ChatGPT -> Cursor Prompt
Cursor -> ChatGPT 결과
ChatGPT -> 새 ChatGPT Handoff
~~~

Engineering System 1.3.x에서 repository-scoped AI Work Packet과 /resume을 도입해 이 수작업을 줄였습니다.

## Full Adoption 전에도 Resume이 가능해야 했다

실제 릴리스 브랜치에서 중요한 예외 상황이 발견됐습니다. 제품 릴리스 작업에는 정상적인 Work Packet이 있었지만 Engineering System 적용은 별도 PR에서 진행 중이었습니다.

이때 local `AGENTS.md`나 `.engineering/*`가 없다는 이유만으로 resume을 중단하면 release 작업과 governance adoption이 섞이게 됩니다.

그래서 resume flow는 adoption이 아직 끝나지 않은 repository를 `ENGINEERING_SYSTEM_ADOPTION=ABSENT_OR_PENDING`으로 기록하고 canonical default 아래에서 계속 진행하도록 보강했습니다. Active workstream이 명시적으로 승인하지 않는 한 adoption 파일은 건드리지 않습니다.

여기서 얻은 교훈은 단순합니다. **Continuity tooling은 자신이 동작하기 위해 product scope를 바꾸지 말고 현재 repository 상태를 관찰해야 합니다.**

## Adoption 자체도 자동화가 필요했다

1.3.x에서 lifecycle과 session continuity는 갖춰졌지만 다른 repository에 시스템을 실제 적용하는 과정은 여전히 AI가 template을 얼마나 잘 해석하느냐에 의존했습니다.

Engineering System 1.4에서는 canonical adoption standard와 deterministic bootstrap을 추가했습니다.

목표 흐름은 다음과 같습니다.

~~~text
"이 프로젝트에 Engineering System을 적용해줘"
  -> Inventory
  -> 기존 Rule 분류
  -> Test / CI 탐색
  -> Immutable Baseline Pin
  -> Shared / Native CI 결정
  -> Bootstrap
  -> Adoption Qualification
~~~

자동화라고 해서 blind overwrite를 하지 않습니다. Ambiguous하거나 destructive한 결정은 fail-closed로 중단합니다.

## 1.5에서는 책임과 운영 상태를 명시적으로 기록

Engineering System 1.5는 AI가 추측하면 안 되는 경계를 더 명확히 했습니다.

- 적용된 저장소는 변경되지 않는 기준 SHA와 변경 범위 검증을 shared/native CI 중 어디서 담당하는지 기록
- native 모드에서는 해당 검증을 담당하는 실제 workflow 파일을 명시
- merge gate는 workflow 파일 존재만 보고 추측하지 않고 `verified`, `advisory`, `unknown`으로 기록
- production-oriented project는 runbook과 incident-response posture를 명시
- material design-bearing change는 최소 design gate로, production-impacting failure는 incident lifecycle로 routing

목표는 문서를 늘리는 것이 아니라 숨어 있던 운영 가정을 명시하면서 implementation context는 작게 유지하는 것입니다.

## 1.5.1에서는 리뷰 피드백 처리를 명시적인 완료 조건으로 만들었습니다

실제 product PR에서 required CI는 모두 통과했지만, configured automated reviewer가 non-blocking `COMMENTED` review에 actionable finding을 남긴 상태로 merge될 수 있는 문제가 확인됐습니다.

Engineering System 1.5.1부터는 **리뷰 상태**와 **리뷰 내용**을 구분합니다. 병합이나 최종 완료 전에 수정이 필요한 피드백은 반영 후 다시 검증하고, 반영하지 않는 피드백은 그 이유를 기록해야 합니다. 단순히 리뷰 상태가 advisory라는 이유만으로 리뷰가 끝났다고 보지 않습니다.

모든 comment에 approval을 요구하는 무거운 절차가 아니라, 실제 actionable finding이 조용히 무시되지 않도록 하는 최소 correctness gate입니다.

## 설계 원칙

> 반복 수작업을 없애거나 correctness를 명확히 높이는 경우에만 automation을 추가합니다.

Solo developer workflow가 enterprise process처럼 비대해지는 것을 막기 위한 기준입니다.
