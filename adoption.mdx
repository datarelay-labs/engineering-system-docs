# Adoption guide

Adoption should reduce context, not add another layer of duplicate rules.

## The intended entrypoint

The user-facing entrypoint is deliberately version-independent:

~~~text
Apply https://github.com/datarelay-labs/engineering-system to this project.
~~~

The agent resolves the exact target repository, obtains the canonical Engineering System from that URL, pins an immutable canonical baseline SHA, then follows `standards/ADOPTION.md` and performs a repository-specific audit before changing files.

The target repository does **not** need to contain `tools/adopt.py` beforehand. The agent may use an authenticated GitHub integration or a separate temporary checkout of `datarelay-labs/engineering-system`, then run the canonical helper against the target root. The canonical source is tooling; it is not vendored into the product repository.

~~~mermaid
flowchart LR
    A["Inventory"] --> B["Classify Rules"]
    B --> C["Discover Tests / CI / Release"]
    C --> D["Choose CI Mode"]
    D --> E["Deterministic Bootstrap"]
    E --> F["Adoption Qualification"]
~~~

## Deterministic bootstrap

Read-only audit:

~~~bash
python tools/adopt.py --root /path/to/project --audit
~~~

Apply after rule/CI review:

~~~bash
python tools/adopt.py \
  --root /path/to/project \
  --apply \
  --ack-rule-review \
  --ci-mode shared \
  --test-command "<project-native test command>"
~~~

The bootstrap installs only missing common surfaces and does not overwrite existing project files.

### Fail-closed boundaries

Adoption stops instead of guessing when:

- the worktree is dirty
- existing AI/engineering rules have not been reviewed
- more than one plausible test command exists
- existing CI is present but shared/native ownership has not been decided
- an existing adoption would need destructive overwrite
- the immutable canonical baseline cannot be resolved

## Managed adoption identity

Managed adopted repositories record enough identity to prove exactly which canonical standard and which project-native gates are in force:

```yaml
engineering_system:
  version: "1.6.0"
  mode: adopted
  baseline: "<40-character canonical commit SHA>"
  ci_mode: native
  native_ci_workflows:
    - ".github/workflows/project-ci.yml"
  merge_gate_status: verified

operations:
  production_oriented: true
  runbook_required: true
  incident_response_required: true
```

`ci_mode` can be `shared` or `native`.

- **shared** uses the Engineering System reusable affected-test workflow.
- **native** preserves existing project CI, maps the concrete workflow files that own the affected-test invariant, and keeps the generated Engineering System workflow compliance-only.
- `merge_gate_status` is `verified`, `advisory`, or `unknown`; never infer branch protection merely because workflows exist.
- Production-oriented repositories explicitly record runbook and incident-response posture.

Current managed adoption also routes material design-bearing changes through the lightweight `standards/DESIGN.md` gate and production-impacting failures through `standards/OPERATIONS.md`. For production-oriented projects it records project-native runbook/health/recovery contracts, reconciles observable GitHub merge enforcement, and uses an executable release contract when real project-native commands exist. This does not require a new design document or incident document for every task; the smallest durable artifact that fits the decision remains preferred.

## New or empty repository

A brand-new project still needs an explicit Git repository boundary because branch, HEAD, history, and reviewable change are part of the safety model. Establish or initialize the intended repository first, then use the same link-only adoption flow.

If there is genuinely no executable product code yet, `--allow-no-tests` may be used as a temporary bootstrap state. It is not a permanent testing exemption: once executable implementation begins, establish real project-native tests and update the affected-test contract before normal development/release qualification is considered complete.

Do not invent a framework, product architecture, release command, or operations contract merely to make adoption look complete.

Start with the canonical templates from:

[github.com/datarelay-labs/engineering-system](https://github.com/datarelay-labs/engineering-system)

Base adoption requires:

~~~text
AGENTS.md
.engineering/project.yaml
.engineering/tests.yaml
.engineering/release.yaml
~~~

Pin the Engineering System version used by the repository.

If you use Cursor and session continuity, add the tool adapter and continuity files separately:

~~~text
.cursor/rules/engineering-system.mdc
.cursor/commands/resume.md
.github/ISSUE_TEMPLATE/ai-work-packet.md
~~~

This distinction matters: base engineering governance and AI session continuity are related, but not the same feature.

## Existing repository with many AI rules

Do not blindly add another always-on rule.

First classify the existing rules:

~~~text
KEEP
KEEP_STRICTER
DUPLICATE
CONFLICT
OBSOLETE
UNKNOWN
~~~

Keep product-specific invariants and stricter valid rules.

Move generic duplicated engineering guidance back toward the canonical Engineering System so Cursor context becomes smaller rather than larger.

## Adoption-pending repositories

A valid Work Packet may exist before the repository has completed Engineering System adoption.

When `AGENTS.md` or `.engineering/*` are missing during resume:

- record `ENGINEERING_SYSTEM_ADOPTION=ABSENT_OR_PENDING`
- continue under the canonical Engineering System default when the Work Packet is otherwise valid
- do not silently create, merge, or modify adoption files unless the active workstream explicitly authorizes adoption work

This lets release or feature work continue without accidentally mixing governance adoption into the product change.

## Install the Cursor resume command

On the machine running Cursor:

~~~bash
mkdir -p ~/.cursor/commands
curl -fsSL https://raw.githubusercontent.com/datarelay-labs/engineering-system/main/.cursor/commands/resume.md \
  -o ~/.cursor/commands/resume.md
~~~

This provides the continuity command to Cursor. In the normal owner workflow, ChatGPT starts Cursor CLI and hands it the repository `/work-resume` flow; the owner does not need to type `/resume` manually.

## Add ChatGPT routing, not the whole standard

ChatGPT Custom Instructions should stay short.

They only need to say:

- use the canonical Engineering System
- resolve the repository first
- use Work Packets for Cursor handoff and chat continuity
- read only minimal relevant context
- never claim unexecuted or different-HEAD evidence as PASS

Do not copy every Engineering System standard into Custom Instructions.

## Optional: connect Desktop Commander

For direct development-host audit, connect Desktop Commander Remote MCP and restrict it to the intended development paths.

This is optional. GitHub remains the durable baseline even when remote audit is available.

## Adoption qualification

File presence alone is not PASS.

Managed adoption validates required surfaces, version/baseline identity, session-continuity files, baseline-pinned caller workflows, test metadata, CI ownership, and release wiring when configured.

Then run the repository's cheapest real project-native smoke/affected test.

Only after deterministic validation and required smoke evidence succeed should the result be reported as:

~~~text
ENGINEERING_SYSTEM_ADOPTION=PASS
~~~

## Session continuity smoke test

A simple continuity smoke test is:

~~~text
ChatGPT:
"Cursor에 넘겨줘"
  -> Work Packet + branch/worktree
  -> ChatGPT starts Cursor CLI
  -> Cursor follows `/work-resume`

ChatGPT:
"Cursor 끝났어. 계속"
  -> independently verify GitHub/CI/PR/issue/worktree state
~~~

If the same workstream resumes without copying a large prompt, the continuity path is working.
