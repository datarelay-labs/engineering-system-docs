# System architecture

The system gives each tool one primary job instead of asking a single AI tool to do everything.

## System layers

~~~mermaid

    H["Human Layer<br/>engineering.datarelay.run"]
    K["Knowledge Layer<br/>Athena"]
~~~

The handbook and Athena help people understand and find context. Current product and release state should be checked against GitHub and the results of tests or runtime verification.

## Responsibility map

| Component | Primary responsibility | Do not use it as the final reference for |
|---|---|---|
| Owner | Product requirements, scope, final decisions, release approval, human UX judgment | Implementation detail unless explicitly decided |
| ChatGPT | Requirements, architecture, repository implementation, affected tests, review, coordination, audit | Current Git state unless freshly observed |
| Cursor | Optional per-packet compatibility implementation after explicit `IMPLEMENTER=CURSOR` opt-in | Default implementation authority |
| Automation / CI | Repeatable validation, security/performance gates, artifact verification | Product intent |
| GitHub | Code, history, PRs, CI, specs, Work Packets, release evidence | Human-friendly narrative |
| Desktop Commander Remote MCP | Direct audit of authorized development hosts | Durable project history |
| Athena | Searchable decision and history layer | Current runtime state or release verification |
| Engineering System | Shared engineering rules and AI workflow | Product-specific behavior |
| Engineering System Docs | Human-readable handbook | The rules enforced by the Engineering System repository |

## Authority order

When information conflicts, use this order:

1. actual code, config, schema, runtime, and immutable Git state
2. canonical product/specification artifacts
3. repository engineering metadata
4. executed deterministic test and CI evidence
5. AI Work Packet current coordination state
6. Athena / derived documentation
7. conversation history

This order prevents a stale chat, roadmap, or wiki page from silently overriding the current product.

~~~mermaid

    A["1. Code / Config / Schema / Runtime / Git"] --> B["2. Canonical Product Spec"]
    B --> C["3. Repository Engineering Metadata"]

    D --> E["5. AI Work Packet"]
    E --> F["6. Athena / Derived Docs"]
    F --> G["7. Conversation History"]
~~~

## Two repositories, two purposes

**datarelay-labs/engineering-system**

This repository contains the rules, adapters, templates, validation logic, `/resume`, and session-continuity behavior used by projects and agents.

**datarelay-labs/engineering-system-docs**

This site explains why the system exists, how the pieces fit together, how to adopt it, and what problems it solves.

<Warning>
  If this site differs from the Engineering System repository, follow the repository.
</Warning>

## Project-local adoption

Base Engineering System adoption requires the small repository entrypoint used by agents and CI:

~~~text
AGENTS.md
.engineering/project.yaml
.engineering/tests.yaml
.engineering/release.yaml
~~~

The AI Work Packet Issue template is the continuity/authority surface. Cursor-specific session files such as `.cursor/commands/resume.md` are compatibility adapters and remain disabled by default unless a packet explicitly opts into Cursor.

A product repository should not copy every Engineering System rule into itself. It should pin the Engineering System version and baseline, then reference the relevant standards.
