# Data Relay Engineering System

**ChatGPT for requirements and design. Cursor for implementation. GitHub for durable records. Direct server access for verification.**

This system grew from a practical problem: AI-assisted development was useful, but the surrounding process became expensive, repetitive, and hard to keep consistent.

Large handoff prompts, stale roadmaps, repeated Cursor instructions, missing design history, full-suite tests at the wrong time, and manual copy/paste between tools all created friction.

The current system separates each responsibility and keeps only the minimum context needed for the next action.

## The core idea

~~~mermaid
flowchart LR
    U[Owner] <--> C[ChatGPT]
    C --> W[GitHub AI Work Packet]
    W --> R[ChatGPT starts Cursor /work-resume]
    R --> G[Code / Tests / Git]
    G --> CI[CI & Release Evidence]
    CI --> C
    C <--> D[Desktop Commander - Development Server]
    G --> A[Athena - Derived Knowledge]
    R --> T[Telegram - Completion Signal]
~~~

<Note>
  GitHub holds the durable engineering record. Athena, this handbook, and AI Work Packets support search, explanation, and active-work coordination.
</Note>

## Why this split works

ChatGPT is used heavily before implementation: requirements, brainstorming, architecture, design, documentation, review strategy, and the exact next action.

Cursor is used when code must actually change. Keeping exploration separate from implementation reduces unnecessary context and gives the coding task a clear scope.

GitHub holds the durable record: code, tests, specifications, commits, PRs, CI results, release records, and repository-scoped AI Work Packets.

Desktop Commander closes another gap: when GitHub alone is not enough, ChatGPT can inspect the authorized development Linux host directly instead of reasoning only from pasted terminal output.

## Five rules that keep it small

1. Keep durable engineering records in GitHub; use the handbook and Athena to explain and find them.
2. ChatGPT plans and reviews; Cursor implements work with a clearly defined scope.
3. Load only the context needed for the current task.
4. Run affected deterministic checks before expensive broad qualification.
5. Keep active session state in repository-scoped Work Packets, not giant handoff prompts.

## What this system is not

It is not an enterprise process framework, a central project-management database, or a replacement for Git.

It is a small set of rules that makes a solo AI-assisted workflow repeatable, reviewable, and practical to use every day.

<Tip>
  If you remember only one rule: **conversation is temporary; durable decisions and work state belong in the repository.**
</Tip>
